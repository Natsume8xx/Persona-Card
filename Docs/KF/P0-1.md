### 1.2 目标流程（GDD 2.6，白盒初值）

```
装备确认
 → 节点0 普通战 350 → 奖励 → 商店1
 → 节点1 Boss战 550（初级池） → 奖励 → 商店2
 → 节点2 普通战 1000 → 奖励 → 商店3
 → 节点3 Boss战 1500（中级池） → 奖励 → 商店4
 → 节点4 普通战 2800 → 奖励 → 商店5
 → 节点5 Boss战 4200（高级池） → 局终报告 → 铸牌 → 收藏/装备 → 主菜单
```

Boss 战开战前保留现有 `BossReveal` 揭示阶段；普通战商店结束后直接进入战斗。

### 1.3 核心改动设计

#### A. 新增路线表资产 `RunRouteAsset` + 静态访问门面 `RunRoute`

采用 **ScriptableObject 资产 + 静态门面** 双轨结构，是整局流程的唯一权威来源：

- **数据层**（策划可视化编辑）：`RunRouteAsset`（SO 资产，放 `PersonaCards.Data` 程序集——该程序集目前只有占位文件、正好空着，且所有程序集均已引用它，**asmdef 零改动**）。
- **代码层**（程序/状态机访问）：静态门面 `RunRoute`（放 `PersonaCards.UI`），持有当前生效资产；**资产缺失或未赋值时回落内置默认路线（= GDD 白盒表）+ 控制台警告**——纯 SO 方案在"资产被删/忘赋值"时会直接 NPE，jam 项目经不起这种运行时风险。

`Assets/PersonaCards/Data/RunRouteAsset.cs`：

```csharp
namespace PersonaCards.Data
{
    /// <summary>战斗节点类型。</summary>
    public enum RunNodeKind
    {
        /// <summary>普通战斗：无 Boss 规则与介入事件。</summary>
        NormalBattle,
        /// <summary>Boss 战斗：开战前走 BossReveal 揭示阶段。</summary>
        BossBattle
    }

    /// <summary>Boss 难度池（GDD 2.5 共 3 池；P0-3 起由 BossEncounterCatalog 按池出怪）。枚举而非字符串：Inspector 下拉框杜绝策划拼写错误。</summary>
    public enum BossPoolId
    {
        /// <summary>初级池：第一场 Boss。</summary>
        Primary,
        /// <summary>中级池：第二场 Boss。</summary>
        Intermediate,
        /// <summary>高级池：最终 Boss。</summary>
        Advanced
    }

    /// <summary>单局路线中的一个战斗节点（可序列化配置，Inspector 直接编辑）。</summary>
    [Serializable]
    public sealed class RunBattleNode
    {
        [Tooltip("节点类型：普通战或 Boss 战。")] public RunNodeKind kind;
        [Tooltip("本场目标分（GDD 2.6 白盒初值）。")] public long targetScore;
        [Tooltip("Boss 难度池；普通战留空即可。")] public BossPoolId? bossPoolId;
        [Tooltip("胜利后是否进入商店（最终 Boss 为 false，直接局终结算）。")] public bool hasShopAfter;

        /// <summary>节点序号，0 起，资产加载时按列表位置写入，策划无需填写。</summary>
        public int Index { get; internal set; }
    }

    /// <summary>单局路线表资产（GDD 冻结决策 #6：MVP 无分支地图，固定线性流程）。</summary>
    [CreateAssetMenu(menuName = "PersonaCards/RunRoute", fileName = "RunRoute")]
    public sealed class RunRouteAsset : ScriptableObject
    {
        [Tooltip("按顺序排列的战斗节点；节点数即单局战斗总数。")]
        public List<RunBattleNode> battleNodes = new List<RunBattleNode>();

        /// <summary>轻量校验（OnValidate 调用，同时供单元测试直接调用）：节点非空、Boss 节点必须有池 id、只有最后一个节点可 hasShopAfter=false 等。</summary>
        public bool Validate(out string error);
    }
}
```

`Assets/PersonaCards/UI/RunRoute.cs`（静态门面，状态机/控制器的唯一访问口）：

```csharp
namespace PersonaCards.UI
{
    /// <summary>整局流程的唯一权威访问口：数据来自 RunRouteAsset（Inspector 可编辑），资产缺失时回落内置默认路线。</summary>
    public static class RunRoute
    {
        /// <summary>由控制器 Awake 注入路线资产；null 表示回到内置默认路线（供测试与容错）。</summary>
        public static void Configure(RunRouteAsset asset);

        /// <summary>单局战斗总数（= 当前路线节点数，从列表推导，策划无需维护数字）。</summary>
        public static int BattleCount { get; }
        /// <summary>单局商店次数（= hasShopAfter 为 true 的节点数）。</summary>
        public static int ShopCount { get; }
        /// <summary>按顺序排列的战斗节点。</summary>
        public static IReadOnlyList<RunBattleNode> BattleNodes { get; }
        /// <summary>取指定节点；越界抛 ArgumentOutOfRangeException。</summary>
        public static RunBattleNode GetNode(int index);
        /// <summary>是否为最终战斗节点（胜利后进局终报告而非商店）。</summary>
        public static bool IsFinalNode(int index) => index == BattleCount - 1;
        /// <summary>下一战斗是否为 Boss 战（决定商店结束后的去向）。</summary>
        public static bool NextNodeIsBoss(int index);
    }
}
```

设计取舍：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯静态列表（原文档方案） | 零依赖、测试确定 | 调数值要改代码，策划不可编辑 |
| 纯 SO | 策划可编辑 | 资产丢失即崩溃；测试依赖资产；状态机要携带资产实例 |
| **SO + 静态门面（采用）** | 可编辑 + 有兜底 + 状态机 API 不变 | 多一层门面（约 60 行） |

其他决策：

- 资产文件放 `Assets/PersonaCards/Data/RunRoute.asset`，由 `PrototypeFlowController` 的 `[SerializeField]` 字段在场景中拖拽引用，`Awake` 里 `RunRoute.Configure(runRoute)`。这是项目**第一个 SO**——本 P0 只把路线表 SO 化，Persona/Boss/HandType 等目录仍维持静态类（P2 再评估统一数据化，避免范围蔓延）。
- `BossPoolId` 用**枚举**而非自由字符串：GDD 恰好 3 个池，下拉框从根上杜绝策划拼写错误（字符串 id 无编译期检查）。

节点表数据（GDD 2.6 白盒初值，写入 `RunRoute.asset`；内置默认路线同此表）：

| Index | Kind | TargetScore | BossPoolId（P0-3 落地） | HasShopAfter |
|---|---|---|---|---|
| 0 | NormalBattle | 350 | — | true |
| 1 | BossBattle | 550 | `Primary` | true |
| 2 | NormalBattle | 1000 | — | true |
| 3 | BossBattle | 1500 | `Intermediate` | true |
| 4 | NormalBattle | 2800 | — | true |
| 5 | BossBattle | 4200 | `Advanced` | false |

#### B. 状态机改为节点索引驱动

修改 [PrototypeFlowStateMachine.cs](Assets/PersonaCards/UI/PrototypeFlowStateMachine.cs)：

- 删除 `BattleNumber`，新增 `NodeIndex`（0..5，0 起，指向 `RunRoute.BattleNodes`）。
- 转移表变为：

| 方法 | 转移 | 节点变化 |
|---|---|---|
| `StartNewRun()` | MainMenu → PersonaSetup | 清回程标记 |
| `ReturnToPersonaSetup()`（走查反馈修复新增） | BossReveal → PersonaSetup | **保留节点**，置回程标记 |
| `ConfirmPersonaSetup()` | PersonaSetup →（回程标记 ? BossReveal : Battle） | 新局 `NodeIndex = 0`；回程保留节点并消费标记 |
| `CompleteBattle(won)` | 失败 → FailureResult；胜利且 `RunRoute.IsFinalNode(NodeIndex)` → RunReport；胜利非最终 → Reward | — |
| `ContinueFromReward()` | Reward → Shop | — |
| `ContinueFromShop()` | Shop →（`RunRoute.NextNodeIsBoss(NodeIndex)` ? BossReveal : Battle） | `NodeIndex += 1` |
| `BeginBossBattle()` | BossReveal → Battle | —（节点在离开商店时已推进） |
| `ContinueToForge()` | RunReport → PersonaForge | — |
| `Restore(stage, nodeIndex, personaSetupReturnsToBossReveal)` | 恢复 | 校验 0..5；回程标记仅 PersonaSetup 阶段生效 |
| `ReturnToMainMenu()` | → MainMenu | `NodeIndex = 0` + 清回程标记 |

- `Restore` 的边界校验从 `battleNumber <= 3` 改为 `nodeIndex <= RunRoute.BattleCount - 1`。

#### C. 控制器去硬编码

修改 [PrototypeFlowController.cs](Assets/PersonaCards/UI/PrototypeFlowController.cs)：

1. **局种子**：新增 `_runSeed` 字段，`StartNewRun()` 时用 `unchecked((uint)System.Environment.TickCount)` 生成；场次种子派生为 `unchecked(_runSeed + (uint)(node.Index + 1))`——同局可复现（存进存档），不同局不同序。
2. **`StartCurrentBattle()`** 改为读路线表：

```csharp
private void StartCurrentBattle()
{
    var node = RunRoute.GetNode(_flow.NodeIndex);
    var seed = unchecked(_runSeed + (uint)(node.Index + 1));  // 场次种子由局种子派生，保证同局复现
    var boss = node.kind == RunNodeKind.BossBattle
        ? BossEncounterCatalog.CreateFromPool(node.bossPoolId)  // P0-1 临时返回镜厅守门人
        : null;
    battleController.BeginBattle(node.targetScore, seed, _journeyDeck.CreateBattleDeck(),
        _personaLoadout.CreateLoadout(), boss);
    battleProgressText.text = $"旅程 {node.Index + 1} / {RunRoute.BattleCount}";
}
```

> 实施备注：`BossPoolId` 用 `None = 0` 哨兵值而非可空枚举——Unity 序列化不支持 `Nullable<T>`，可空字段在 SO 资产里会被静默跳过。

3. **奖励节点状态重置**：`OnBattleCompleted` 进入 Reward 分支时补 `_rewardClaimed = false;`。旧流程只有 1 次奖励节点所以没暴露；新流程 5 次奖励节点，必须在每次进入时重置。
4. **修复已知 bug（顺手）**：`ReturnToPersonaSetup()` 重启新局时目前不会重建牌库（旧牌库带入新局）。抽取 `InitializeRun()` 私有方法（重建 52 张牌库、重置金币、新局种子），`StartNewRun` 使用。（*注：走查反馈后 `ReturnToPersonaSetup` 语义已改，不再重建牌库，见 §1.5*）
5. **Boss 揭示文案**：目标分数改为读当前节点（`RunRoute.GetNode(_flow.NodeIndex).targetScore`）；Boss 名称/规则文本 P0-1 暂仍显示镜厅守门人（加 `// TODO(P0-3/P0-9)` 注释），保持可编译可演示。
6. **存档**：`PrototypeSaveData` 新增 `runSeed` 字段；原 `battleNumber` JSON 字段**保留字段名**（JsonUtility 按名序列化，改名会让旧档静默丢数据），语义改为节点索引，代码注释注明 P0-8 升 schema v4 时重命名为 `nodeIndex`。`Save()` 写 `_flow.NodeIndex` 与 `_runSeed`；`ContinueSavedRun` 读取并 `_flow.Restore(stage, nodeIndex)`。
7. **Boss 目录桥接**：[BossEncounterCatalog.cs](Assets/PersonaCards/Battle/Bosses/BossEncounterCatalog.cs) 新增 `CreateFromPool(BossPoolId poolId)`——P0-1 临时实现：任意池 id 一律返回 `CreateMirrorKeeper()`（`// TODO(P0-3)` 换成三难度池 + 抽取逻辑）。Battle 程序集已引用 Data 程序集，枚举可直接使用。**实施备注**：Battle 程序集是 `noEngineReferences` 纯逻辑层，`Debug.LogWarning` 不可用——"难度池未落地"警告改由 UI 层 `StartCurrentBattle` 打点（`[Boss]` 前缀）。

### 1.5 走查反馈修复（2026-08-18 第二轮）

**问题 1（已修复）**：Boss 揭示界面点"返回检查装备"，确认装备后理应回到刚才的 Boss 节点，实际却回到了第 0 节点。

- 原因：旧实现 `ReturnToPersonaSetup()` = 放弃本局并重开（`ReturnToMainMenu` + `StartNewRun`，节点清零、牌库重建、种子重roll）；且 `ConfirmPersonaSetup()` 无条件 `NodeIndex = 0`，没有区分"新开局确认"与"装备检查返回确认"。
- 修复：语义改为**保留本局**——`ReturnToPersonaSetup()` 仅做 BossReveal → PersonaSetup 转移并置回程标记（牌库/种子/节点全保留）；`ConfirmPersonaSetup()` 按回程标记分支：新局进第 0 节点战斗，回程则返回 Boss 揭示界面（节点不变，战斗未开始无需重建场次），标记消费后清除。标记随存档持久化（`PrototypeSaveData.personaSetupReturnsToBossReveal`），中途退出再继续游戏仍能正确回程；旧档缺该字段默认 false，行为与新局一致。
- 状态机 API 变化：新增 `ReturnToPersonaSetup()` 方法与 `PersonaSetupReturnsToBossReveal` 属性；`Restore` 增加可选参数 `personaSetupReturnsToBossReveal`（默认 false，仅 PersonaSetup 阶段生效）；`ReturnToMainMenu()` / `StartNewRun()` 清标记。

**问题 2（待讨论，未改动）**：商店继续按钮文案写死"进入Boss战"，普通节点后也显示同样文案。方案见"待讨论"清单，确认后再改。

**问题 3（后续 P0）**：战斗金币循环未实装（整局仅初始 3 金币，无战斗收入/商店经济联动），归属 P0-6 经济与奖励内容改造。

**问题 4（已修复）**：战斗中退出游戏 → "继续游戏"看起来加载了旧版存档（顶部进度显示"旅程 1 / 3"）。

- 排查结论：读到的档其实**就是当前新档**，问题出在两点：① 快照恢复路径（`ContinueSavedRun` 恢复战斗快照）不经过 `StartCurrentBattle`，没人刷新 `battleProgressText`，顶部显示的是**场景里残留的默认文案**"旅程 1 / 3"（场景构建器已改成 1 / 6，但标记对象名未变、场景未触发重建，旧文案一直留在场景里）；② 旧档读取失败时玩家会卡在残缺界面，没有回退。
- 修复：快照恢复后显式刷新 `battleProgressText = $"旅程 {_flow.NodeIndex + 1} / {RunRoute.BattleCount}"`；场景 `Journey Progress` 文本原地改为"旅程 1 / 6"并保存；`ContinueSavedRun` 的 catch 改为回退主菜单 + 禁用继续按钮（存档保留原样，新开一局会整体覆盖）。
- 存档机制完整说明见文末"五、存档机制说明"。

## 三、开发后测试内容

### 3.1 单元测试（EditMode，Unity Test Runner）

**`RunRouteTests`（新增）**：

## 五、存档机制说明（走查反馈追加，2026-08-18）

### 5.1 存档存到哪里？继续游戏读的是什么？

- **本地单槽位 JSON 文件**：[PrototypeSaveStore.cs](Assets/PersonaCards/UI/PrototypeSaveStore.cs) 负责读写，文件路径 `Application.persistentDataPath/persona-cards-save-v1.json`（macOS 上约在 `~/Library/Application Support/<公司名>/<产品名>/`）。
- 全游戏只有**这一个存档文件**：人格收藏、当前装备、活动旅程进度全部装在里面。写盘采用"临时文件 + 原子替换 + .bak 备份"三步，防止写一半断电损坏。
- **"继续游戏"读的就是这个本地文件**：`Awake` 时 `TryLoad` 一次，`hasActiveRun == true` 才点亮"继续游戏"按钮；点按钮时再读一次并整体恢复（`ContinueSavedRun`）。没有网络存档、没有多槽位。

### 5.2 什么时候触发存档？

所有存档都在关键状态变化点**即时写盘**（没有定时器、没有退出时统一保存）：

| 时机 | 方法 | hasActiveRun |
|---|---|---|
| 开始新局 | `StartNewRun` | true |
| 每场战斗开战 | `StartCurrentBattle` | true |
| **战斗中**出牌/弃牌等稳定状态变化 | `battleController.StableStateChanged` → `SaveActiveRun` | true |
| 战斗结算（胜负） | `OnBattleCompleted` | true |
| 领取奖励进商店 | `ContinueFromReward` | true |
| 离开商店（进 Boss 揭示或下一战） | `ContinueFromShop` | true |
| Boss 揭示返回检查装备 / 确认装备 | `ReturnToPersonaSetup` / `ConfirmPersonaSetup` | true |
| 局终报告进铸造 | `ContinueToForge` | true |
| 商店购买（删牌/重刻/强化） | `Purchase` | true |
| 回到主菜单（本局结束） | `ReturnToMainMenu` → `SaveInactiveProfile` | **false** |
| 铸造确认（获得人格，回收藏） | `ConfirmForgeCandidate` → `SaveInactiveProfile` | **false** |
| 收藏界面换装备 | `SaveProfileOnly` | 保持原值（只覆盖收藏/装备字段） |

### 5.3 存档存了哪些东西？（PrototypeSaveData 字段全表）

| 字段 | 内容 |
|---|---|
| `schemaVersion` | 存档格式版本（当前 3，P0-8 升 v4） |
| `hasActiveRun` | 是否有进行中的旅程（决定"继续游戏"按钮） |
| `stage` | 当前流程阶段（MainMenu/PersonaSetup/Battle/Reward/Shop/BossReveal/RunReport/PersonaForge/FailureResult） |
| `battleNumber` | **当前战斗节点索引**（JSON 字段名沿用旧名以兼容旧档，P0-8 改名 nodeIndex） |
| `personaSetupReturnsToBossReveal` | 装备阶段是否由 Boss 揭示返回（回程标记） |
| `runSeed` | 局种子：场次种子 = runSeed + 节点 + 1，保证读档后手牌顺序一致 |
| `coins` | 当前金币 |
| `selectedJourneyCardIndex` / `rewardClaimed` | 奖励/商店界面选中的牌与奖励是否已领取 |
| `deck` | 整副旅程牌组（52 张起，含每张牌的删除/强化/重刻状态） |
| `collection` / `equipped` | 人格收藏与当前 3 槽装备 |
| `behavior` | 行为统计：出牌/弃牌次数、累计得分、各牌型次数（局终报告与铸造用） |
| `battle` | **战斗内快照**：目标分/当前得分/剩余出牌弃牌次数/抽牌堆/手牌/已出/弃牌堆/选中的牌/Boss 遭遇状态（仅战斗中且非演出锁定时写入） |

### 5.4 读档恢复流程（ContinueSavedRun）

1. 读 JSON → 重建 `_journeyDeck`（牌组）、`_personaLoadout`（装备）、`_behaviorTracker`（统计）。
2. `_flow.Restore(stage, battleNumber, 回程标记)` 恢复状态机位置（非法值抛异常 → 回退主菜单并禁用继续按钮）。
3. 若阶段是 Battle：有快照则 `RestoreBattle`（完整恢复战斗现场并刷新进度文案），无快照则 `StartCurrentBattle` 重开本场。
4. 渲染界面。旧档兼容：缺 `runSeed` → 0（场次种子退化为节点+1，仍可复现）；缺回程标记 → false（等同新局）。

### 5.5 已知边界（P0-8 统一处理）

- `battleNumber` 字段名未改（JsonUtility 按字段名映射，改名会让旧档静默丢数据），语义已是节点索引。
- 单槽位设计：新开一局会整体覆盖旧旅程（无历史档）；人格收藏/装备与旅程进度同档。
- 旧版本（3 场战斗版）留下的存档文件会被当作合法档读取——若 `hasActiveRun=true` 且字段语义相同，恢复结果按当前路线表解释；异常时走 5.4 的回退路径。
